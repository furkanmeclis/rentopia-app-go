# WhatsApp channel (TEC-735)

Transactional customer notifications over WhatsApp through a self-hosted
[wuzapi](https://github.com/asternic/wuzapi) gateway (REST on whatsmeow).
Each organization links its own number: one wuzapi user = one WhatsApp Web
session. Module: `backend/internal/modules/whatsapp`, providers:
`backend/internal/platform/whatsapp`. UI: `/t/{slug}/settings/whatsapp`.

## Deployment

- `compose.prod.yml` runs `wuzapi` on the private app network only (no
  public port, not on `dokploy-network`); data in the `wuzapi_data` volume.
- `WUZAPI_ADMIN_TOKEN` and `WUZAPI_ENCRYPTION_KEY` are generated by
  `scripts/prod-env.sh` (`deploy/env/schema` v4); `WUZAPI_IMAGE` should be
  pinned to a tested tag.
- The backend and worker get `WUZAPI_BASE_URL` (the gateway) and
  `WUZAPI_WEBHOOK_BASE_URL` (the API as wuzapi reaches it).
- Without a base URL / admin token the `wuzapi` provider reports
  unavailable. Outside production the `whatsapp_fake` provider is
  registered (links ten seconds after the QR is shown; numbers ending in
  `0000` are not on WhatsApp, `9999` are rejected; receipts follow in
  process).

## Model

| Table | Purpose |
|-------|---------|
| `integration_accounts` (kind `whatsapp`) | Provider `wuzapi` / `whatsapp_fake`. Nothing is typed in: the generated session token, wuzapi user id and webhook token are sealed in the account credentials (`integrations.Vault`); the hint stays empty. |
| `whatsapp_sessions` | One per account: status (`created`, `pairing`, `connected`, `disconnected`, `logged_out`), masked linked number, rate limit per minute (1–60, default 20), who accepted the number risk notice, `alerted_at`, SHA-256 of the webhook token. |
| `whatsapp_messages` | Message log: purpose (`notify.<event>` / `test`), engine delivery uuid, masked recipient + SHA-256 (per-recipient limit), our WhatsApp message id, `queued → sent → delivered → read` or `failed`. No message text (the engine delivery log keeps it). |

All tenant routes need `tenant.integrations.manage` (no new permission).

## Flow

1. **Connect** (`POST /v1/tenant/whatsapp/session/connect`, risk notice
   required): creates the account and the wuzapi user (`POST /admin/users`
   with token, webhook URL, events `ReadReceipt, Connected, PairSuccess,
   LoggedOut, Disconnected`), opens the socket (`/session/connect`).
2. **QR** (`GET …/session/qr`, polled): `/session/qr` data URL until
   `/session/status` reports logged in → `connected` (masked number from
   the JID).
3. **Send** (`notifyengine` channel `whatsapp`, customers only): skipped
   when not linked, no valid number or the number is not on WhatsApp
   (`/user/check`) — the rule's next channel runs. Rate limits (session per
   minute, 10 per recipient per hour) fail the attempt (fallback).
   `/chat/send/text` with our message id; the attempt is `accepted`.
4. **Receipts**: `POST /v1/public/whatsapp/webhook/{token}` (token per
   session, compared in constant time) — `Delivered` settles the engine
   attempt as delivered, `Read` is logged. No delivery receipt within 60
   minutes fails the attempt (the engine falls back, e.g. to SMS).
5. **Health**: the worker task `app:whatsapp:watch` (every 2 minutes) reads
   the state of linked / dropped sessions, retries `connect` for dropped
   ones and expires receipts. A linked session that drops becomes
   `disconnected` and the integration managers get one in-app alert.
6. **Logout** unlinks the phone (session kept); **Remove** deletes the
   wuzapi user and disables the account.

Documents (`Service.SendDocument`, `/chat/send/document`) are available to
features that send a PDF (contract, invoice); the engine sends text with a
link preview when the message carries a link.

## Policy

Only transactional notices: the engine catalog has no marketing events and
the channel refuses `marketing.*` events. The settings page explains the
number risk (an unofficial WhatsApp Web session; bulk or unsolicited sends
can get the number banned) and the organization accepts it before linking.
